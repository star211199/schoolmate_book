### 调研结论（7 个同类项目）
- 专业 IM：V-IM（会话/消息/群组/好友模块拆分 + Bridge 对接外部用户体系）、box-im（Netty，离线消息与群管理）、webchat（Vue3+SpringBoot 微信级闭环，Redis 互踢）、spring-websocket-chat（SpringBoot3+Java21+STOMP，在线状态 presence）。
- 校园社交：campus_team-backend（群聊绑定队伍→印证群聊应绑组织关系）、Alumni-social-system（校友群多对多成员表）、中国同学录（班级资料仅成员可见）。
- 同学录产品：**时光胶囊、班级树洞、青春地图、记忆长廊、通讯录导出** —— 情感化功能，列为 P2 亮点。

### 三条架构主线（本次核心决策）
1. **统一会话模型**：私聊/群聊共用 `chat_session` + `chat_message`，靠 `session_type` 区分 → 前端一套 MessageList.vue 覆盖两种场景。
2. **双通道职责切分**：HTTP 管状态变更（登录、拉历史、加好友、建群），WebSocket 管实时推送（发消息、收消息、已读、在线状态）。
3. **主题三层变量**：Palette（色值）→ Semantic（主题切换的操作对象）→ Component（组件微调），组件里只写 `var(--color-*)`。

### 关键设计决策（备查）
- **好友关系单行存储**：`user_a_id`(小) + `user_b_id`(大) + `uk_pair`，查询用 OR + 双索引；避免两行不一致。
- **会话双层模型**：`chat_session`（共享）+ `chat_session_user`（私有：last_read_message_id / pinned / muted）。置顶免打扰必须放第二层，否则 A 置顶会连带 B。
- **未读数不存字段**：用 `COUNT(*) WHERE session_id=? AND id > lastReadMessageId` 实时算，靠 `(session_id, id)` 索引，永不出现数据不一致。
- **消息先落库再推送**：避免「幽灵消息」。`client_msg_id` 做幂等去重。
- **撤回改 msg_type=RECALL 而不删记录**：硬删会破坏已读位点的连续性。
- **班级群**：`uk_biz(group_type, class_id, deleted)` 从库层保证一班级一群，免分布式锁；成员随 class_member 同步（"确保存在"幂等钩子）。
- **WS 鉴权用 URL 查询参数**：浏览器原生 WebSocket 不支持自定义请求头；放 HandshakeInterceptor 验签，非法 token 直接拒绝握手。不用「连上后发 AUTH 帧」（会白白建立非法连接）。
- **选原生 TextWebSocketHandler 而非 STOMP/@ServerEndpoint**：能注入 Bean、握手可鉴权、原理讲得清。@ServerEndpoint 无法注入 Spring Bean。
- **同意好友时立即建会话**：否则会话列表不出现对方，用户以为没加上。
- **主题防首屏闪烁**：`index.html` head 里同步内联脚本设 `data-theme`，必须在引 CSS 之前。

### 新增 9 张表
friend_request / friendship / friend_group / chat_group / chat_group_member / chat_session / chat_session_user / chat_message / time_capsule。

### 迭代路线
P0 打通链路（好友+私聊+会话列表）→ P1 群聊与主题 → P2 体验补齐（在线状态、@、断线重连补拉、H5 适配）→ P3 亮点功能（时光胶囊、树洞、青春地图、导出）。

### 本次发现并修复的真实缺陷（重要）
1. **幂等命中不补发 ACK**：`sendMessage` 命中 `clientMsgId` 幂等分支时直接 `return`，发送方收不到 `MESSAGE_ACK` → 前端乐观消息永远停在「发送中」。修复：命中幂等时补推一条 `MESSAGE_ACK` 给发送者，仍不重复向会话成员扇出。
2. **超长消息报错不友好**：WS 通道不走 Bean Validation，2500 字内容直接撞 `varchar(2000)` 抛 DB 异常，前端只看到「服务端处理失败」。修复：Service 层显式校验 `MAX_CONTENT_LENGTH=2000`，返回「消息内容不能超过 2000 字」。

### 排查心法（备查）
测试脚本用**固定 clientMsgId** 且会话 id 固定时，第二轮起必然命中幂等分支，表现为「推送时有时无」。定位方法：把 clientMsgId 加上每轮唯一后缀；并用「同时打印发送方与接收方全部帧」的诊断脚本对比 —— 发送方也收不到 ACK 即可判定是幂等分支，而非注册表/推送问题。

### 本次踩到的三个坑（都已写进脚本，可复用）
1. **`application-prod.yml` 里不能再写 `spring.profiles.active`** —— 它本身就是 profile 专属文件，

- **HTTPS 在 TLS 层被拦**（curl code 35，握手 0.3s 即失败），推测与 SNI 有关；用 HTTP 访问即可。
- 附带发现：用 `curl` 手搓 WS 握手会被 Cloudflare 边缘拒成 `400 Can "Upgrade" only to "WebSocket"`，

- 风险：走 HTTP 时流量不加密，密码与聊天内容在公网明文传输，只能用于演示，且 URL 每次重启会变。

### 顺带修掉的一个真实缺陷
`WsHandshakeInterceptor` 拒绝握手时只 `return false`，没设状态码 → 响应变成 **200 空响应体**，
用 curl 探测会误以为握手成功。已改为显式 `response.setStatusCode(HttpStatus.FORBIDDEN)` 并写入原因。

## 第三轮：「点登录报网络异常」的性能问题

用户反馈公网访问上「点登录显示网络异常，请稍后重试，太不稳定了」。
**根因不是后端、也不是隧道不稳，而是前端资源体积**：natapp 免费隧道只有 1Mbps，
登录页要下 49.8 秒，而 axios 超时是 15 秒 —— 必然超时。

诊断证据（很有参考价值）：
- 连续 10 次登录接口压测：**10/10 成功、~210ms** → 后端与隧道都没问题。
- 单资源实测（未加 gzip）：JS 1.24MB/11.5s、CSS 360KB/3.2s、`bg-campus.png` 2594KB/**25.0s**、
  `login-illustration.png` 2220KB/**21.4s** → 登录页合计约 50 秒。
- **关键教训**：第一次测量忘了给 curl 加 `--compressed`，因此误判「gzip 没开」；
  实际 vite preview **内置了 `compression()` 中间件**（`app.use(compression())`），
  带上 `Accept-Encoding` 后 JS 只有 400KB。用 `-I`(HEAD) 也测不到，必须用 GET。

### 做了三件事

**1. 图片全量转 WebP + 降分辨率**（收益最大，94.3%）
- 新增 `scripts/optimize-images.py`（Pillow，按用途定尺寸：头像 256、插画 900×1350、背景 1440×960）。
- 结果：**14.9MB → 0.85MB**，单张最大 2844KB → 204KB。
- 7 张 `.png` 全部替换为 `.webp`，同步改了 6 处前端引用 + `sql/upgrade.sql`，
  以及**数据库里存的路径**（`user.avatar` / `user_profile.cover_image`，用 `REPLACE` 批量改）。
  原 PNG 已删除（git 可恢复）。
- dist 从 **17MB → 2.7MB**。

**2. 修缓存策略**（原本全是 `Cache-Control: no-cache`，每次刷新全量重下）
- 在 `vite.config.js` 加了 `previewCacheHeaders` 插件：
  `/assets/**` → `max-age=31536000, immutable`；`/images/**` → `max-age=604800`；`index.html` 保持 `no-cache`。
- **踩坑**：sirv 是通过 `res.writeHead(status, headers)` 传头的，
  **传入的 headers 优先级高于 `setHeader`**，所以第一次实现（只 `setHeader`）被无声覆盖、完全没生效。
  正解是在 `writeHead` 里把 headers 副本中的 `cache-control` 删掉再 `setHeader`，
  并兼容 `writeHead(status, headers)` / `writeHead(status, statusMessage, headers)` 两种重载。

**3. 超时与报错文案**
- `request.js` 的 timeout 15s → 25s。
- 错误拦截器改为区分「超时」（`ECONNABORTED`）与「连接失败」（无 response），
  分别提示「请求超时，当前网络较慢」/「网络连接失败」，不再一律「网络异常」。

### 验收结果
登录页首屏 **49.8 秒 → 6.1 秒**（0.75MB），头像 1232KB → 12KB。
缓存头、登录、接口、WebSocket 握手 101、全部页面 200 —— 均正常。
顺带确认：SPA 里访问不存在的 `/images/xxx.png` 返回的是 **200 + index.html（text/html, 954B）**，
这是 HTML 回退不是 404，判断文件是否真删要看 Content-Type。

### 剩下的可选优化
主 JS 包 gzip 后仍有 400KB —— 因为 `main.js` 里 `app.use(ElementPlus)` 全量引入
且用 `Object.entries(ElementPlusIconsVue)` 注册了**全部图标**。

## 第二轮：用户反馈「点登录还是报网络异常」→ 真正的根因是 CORS

### 排查过程
1. 先确认服务端是活的：natapp 隧道在线、MySQL/后端/前端进程都在，公网首页 200、登录接口 200（我用
   curl 测的）——**服务端没问题**。
2. 注意到一个关键线索：用户看到的是**旧文案**「网络异常，请稍后重试」。查线上 JS 确认新版本已生效
   （新文案「请求超时」「网络连接失败」都在），说明用户看到的仍是新代码的**兜底分支**：
   `error.response` 存在但没有 `message` 字段时才会走到这句 —— 也就是「服务端返回了非 2xx，
   但响应体不标准」。
3. 按这个推断复现：给请求**加上浏览器一定会带的 `Origin` 头** → 立刻复现
   `403 Invalid CORS request`。

### 根因（三个条件叠加，缺一不可）
1. 浏览器在**非 GET 请求**上一定自动带 `Origin`；GET 不带 → 所以只有写操作失败，页面/列表都正常。
2. `vite.config.js` 的 `/api` 代理配了 `changeOrigin: true`，把 `Host` 改写成 `localhost:8080`；
   Spring 的 `CorsUtils.isSameOrigin` 拿 `Origin` 和 `Host` 比对，于是把**同源请求误判成跨域**。
3. `WebMvcConfig.addCorsMappings` 的 `allowedOrigins` 白名单只有 localhost:5173/127.0.0.1:5173/8081，
   **没有穿透域名** → `checkOrigin` 失败 → 403。

对照实验证据（服务器上直连 8080）：
- 无 Origin → 200
- `Origin: http://ba3b6d6c.natappfree.cc` → **403**
- `Origin` 与 `Host` 都设成穿透域名 → **200**（证明是 Host 与 Origin 不匹配导致）

### 修复
- `WebMvcConfig`：`allowedOrigins(白名单)` → `allowedOriginPatterns("*")`，
  并把 `allowCredentials(true)` → `false`（全项目无 Cookie/Session，鉴权只在 Authorization 头，
  已 grep 确认无 `HttpSession`/`Cookie` 使用）。
- `request.js`：错误拦截器新增一个分支，HTTP 非 2xx 且响应体无 `message` 时，
  直接显示 `请求失败（HTTP <状态码>）：<响应体片段>`，不再笼统压成「网络异常」。

### 验收
- 带 Origin 的登录/发消息/好友申请/OPTIONS 预检 → 全部 200/204，响应头出现
  `Access-Control-Allow-Origin: http://ba3b6d6c.natappfree.cc`。
- `_test_group.py` 补上 Origin 后，经 SSH 端口转发 + 穿透域名 Origin 跑回归 → **45/45 PASS**。

### 附带发现与处理
- **natapp 免费隧道有「突发连接数」限流**：返回 `HTTP/1.0 429 Connections Exceed` /
  `Too much connections in one mintue`。实测 1 次/秒连发 50 次不触发，但几秒内 25 次连接会触发。
  直接对穿透地址跑密集回归会大面积误报，甚至产生**假 PASS**（「非群主解散群被拒」实际是 429）。
  → 回归脚本改为支持 `TEST_BASE` / `TEST_ORIGIN` 环境变量覆盖，用本机转发地址跑、用穿透域名当 Origin。
- **`pkill -f "[x]xx"` 方括号写法也会失效**：同一条 ssh 命令里别处出现该字符串明文时，
  执行者仍会被自己杀掉（这次部署就死在半路，后端被停、jar 没换）。
  → 新增 `deploy/redeploy.sh`，把停止/替换/启动写进脚本文件再执行。
- 演示数据被回归脚本污染，用 `reset-demo.sh` + `start-all.sh` + `seed-demo.sh` 恢复干净
  （class=1 group=1 session=1 message=1 user=2，邀请码 `CLASS01`，距毕业 640 天）。


## 未知接口路径 500 → 404（已修）

- **异常类**：`org.springframework.web.servlet.resource.NoResourceFoundException`（Spring 6.1 起，
  未命中 Controller 的请求落到兜底静态资源处理器上抛出的）。之前只被 `Exception` 兜底捕获，
  于是路径写错也返回 500 并打一整段堆栈。
- 已在 `GlobalExceptionHandler` 新增两个分支：`NoResourceFoundException` 与
  `NoHandlerFoundException` → HTTP **404** + `code 40400`，日志降为一行
  `WARN 接口不存在：GET /api/xxx`。
- 验证：带 token 访问 `/api/users`、`/api/moments`、`/api/this-does-not-exist` → 全部
  `404 {"code":40400,"message":"接口不存在：GET /api/..."}`；`/classes`、`/auth/me`、`/chat/sessions`
  仍 200；`DELETE /classes` 仍是 200 + `40001 不支持的请求方法`（原有约定未动）。
- **注意**：不带 token 时未知路径会先被 JWT 拦截器挡成 401（拦截器注册在 `/**` 上），
  要验证 404 分支必须带上 token。
