按时间轴串起班级大事。你已有时刻（moment），把它从「卡片流」升级为「时间轴」即可。

一键导出班级同学录为 PDF / Excel。用 EasyExcel 或前端打印样式即可，是很实用的一个功能。

毕业倒计时 已完成

上一版已经做了，说明「情感化功能」这条路线是对的，继续沿用它扩展。

调研结论：三条设计原则 ① 消息模型统一——私聊和群聊共用一张消息表，否则前端要维护两套 UI，代码量翻倍；
② 组织关系复用——群聊绑定已有的班级（class_member），不另起一套成员体系；
③ 主题与业务解耦——所有颜色走 CSS 变量，组件里绝不写死色值，否则加主题要改几十个文件。

3.2 HTTP 与 WebSocket 的职责划分

这是最容易做错的地方。不要把 WebSocket 当成万能通道，否则连接一断整个应用就瘫了。原则是：改变状态的操作用 HTTP，需要实时性的推送用 WS。

场景走哪条通道原因
登录 / 注册 / 获取用户信息HTTP一次性的请求-响应，无实时性要求
加载历史聊天记录HTTP分页查询，天然适合 REST
加载会话列表 / 好友列表HTTP页面初始化时拉取，断网也能重试
发好友申请 / 同意 / 拉人建群HTTP写操作需要明确的事务结果，失败要能重试
发送聊天消息WS要即时到达，且需要服务端回执
接收新消息 / 好友申请通知WS服务端主动推送，HTTP 做不到
已读回执 / 正在输入 / 在线状态WS高频、轻量、可容忍丢失
一个关键设计：消息「先落库，再推送」 发消息时，服务端先在数据库写入消息记录并生成消息 ID，然后才向接收方推送。这样即使推送失败（对方离线、连接抖动），消息也已经在库里，对方下次上线补拉就能拿到。反过来先推送再落库，一旦落库失败，对方就收到一条「幽灵消息」，刷新后就消失了。

3.3 WebSocket 实现方案选型

调研的四个 IM 项目里，三种方案都有人用。我推荐原生 TextWebSocketHandler + 自建会话表，理由如下：

方案优点缺点结论
@ServerEndpoint
JSR-356		 注解式，代码最少 由容器管理实例，无法直接注入 Spring Bean，要用静态变量兜住 service，很别扭 不推荐
STOMP
Spring Messaging		 订阅/广播模型规范，群聊扇出天然契合 概念多（broker、destination、channel），前端要引入 stomp.js；出问题不好排查 备选
TextWebSocketHandler
Spring 原生		 能注入 Bean，握手拦截器可做 JWT 鉴权，自己维护 Map<userId, Set<Session>>，逻辑完全可控、原理讲得清 广播要自己写循环 采用
前提说明：单机部署 自建会话表意味着在线用户必须在同一个 JVM 里。毕设/演示场景单机完全够用。如果以后要多节点部署，扩展点已经留好了：把「向某用户推送」这个动作从「遍历本地 Session」改为「发一条 Redis Pub/Sub 消息，各节点收到后各自推给本地连接」即可，业务代码不用改。

04数据模型

新增 9 张表。所有表沿用你现有约定：id / create_time / update_time / deleted 四件套，逻辑删除 + 唯一索引带 deleted 列。

4.1 三个关键设计决策

决策一：好友关系存一行，而不是两行

A 和 B 成为好友，有两种存法：存两行（A→B、B→A）或存一行（小 id 在前）。

-- 采用：单行 + 双向查询
CREATE TABLE friendship (
  user_a_id BIGINT NOT NULL COMMENT '较小的 userId',
  user_b_id BIGINT NOT NULL COMMENT '较大的 userId',
  ...
  UNIQUE KEY uk_pair (user_a_id, user_b_id, deleted)
);

-- 查询「我的好友」时：
SELECT * FROM friendship
WHERE (user_a_id = #{me} OR user_b_id = #{me}) AND deleted = 0;
  • 写入只有一次，不存在两行不一致的风险（删好友时只删一行，不会出现单向残留）
  • 关系天然无方向，符合「好友」的语义
  • 代价：查询要用 OR，所以两个字段上都要建索引

决策二：会话（session）与消息（message）拆表，并用双层会话模型

这是让「私聊和群聊用同一套 UI」的关键。参考了 V-IM 的会话模型。

chat_session       会话实体：一个私聊关系 / 一个群 = 一行
   biz_key         业务唯一键 → 私聊 "P_1_2"（小 id 在前）、群聊 "G_8"
   session_type    PRIVATE / GROUP

chat_session_user  用户会话状态：每个用户对每个会话有一行
   last_read_message_id   已读到哪条 → 未读数 = 该会话新消息数 - 已读数
   pinned / muted         置顶、免打扰（用户维度，不能放在会话表上）
为什么置顶/免打扰必须拆到第二张表？ 如果放在 chat_session 上，那么 A 把群置顶了，B 那边也一起置顶了——这显然是错的。会话是共享的，会话状态是私有的，必须两层。

决策三：未读数不存字段，用 last_read_message_id 实时算

常见做法是在成员表上存一个 unread_count 字段，每次发消息给所有成员 +1。问题很多：并发下会丢更新、要事务、群大了性能差、数据不一致了还没法修。

-- 未读数直接算出来，永远准确，不需要维护
SELECT COUNT(*) FROM chat_message
WHERE session_id = ? AND id > #{lastReadMessageId}
  AND sender_id <> #{me} AND deleted = 0;

配合 (session_id, id) 联合索引，这个查询极快，而且永远不会有数据不一致。

4.3 核心表结构

chat_message —— 全系统最关键的一张表

CREATE TABLE `chat_message` (
  `id`            BIGINT NOT NULL AUTO_INCREMENT,
  `session_id`    BIGINT NOT NULL              COMMENT '会话ID',
  `sender_id`     BIGINT NOT NULL              COMMENT '发送者ID',
  `msg_type`      VARCHAR(20) NOT NULL DEFAULT 'TEXT'
                  COMMENT 'TEXT/IMAGE/FILE/SYSTEM/RECALL',
  `content`       TEXT                         COMMENT '文本内容(已做XSS转义)',
  `extra`         VARCHAR(1000) DEFAULT NULL   COMMENT 'JSON: 图片URL/文件名/被@的userId数组',
  `reply_to_id`   BIGINT DEFAULT NULL          COMMENT '引用回复的消息ID',
  `client_msg_id` VARCHAR(64) DEFAULT NULL     COMMENT '前端生成的幂等ID，防重复发送',
  `send_time`     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `create_time`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `update_time`   DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP
                  ON UPDATE CURRENT_TIMESTAMP,
  `deleted`       TINYINT(1) NOT NULL DEFAULT 0,
  PRIMARY KEY (`id`),
  KEY `idx_session_id_id` (`session_id`, `id`)   -- 拉历史 + 算未读数
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='聊天消息';

设计要点：

  • 不存 receiver_id。私聊的接收方可以从 session 推出，群聊的接收方是成员列表。存了反而冗余，且群聊时不知道该存谁。
  • client_msg_id 做幂等。网络抖动时前端可能重发，服务端用它去重，避免用户看到两条一样的消息。
  • 消息 ID 单调递增（自增主键），这直接成为「已读位点」的比较依据——已读位点本质就是「我读到的最大消息 ID」。
  • 撤回不删记录，把 msg_type 改成 RECALL，前端渲染成「对方撤回了一条消息」。硬删除会破坏已读位点的连续性。

chat_group —— 群

CREATE TABLE `chat_group` (
  `id`           BIGINT NOT NULL AUTO_INCREMENT,
  `group_name`   VARCHAR(100) NOT NULL,
  `avatar`       VARCHAR(255) DEFAULT NULL,
  `group_type`   VARCHAR(20) NOT NULL DEFAULT 'CUSTOM'
                 COMMENT 'CLASS=班级自动群 / CUSTOM=自建群',
  `class_id`     BIGINT DEFAULT NULL          COMMENT '班级群关联的班级ID',
  `owner_id`     BIGINT NOT NULL              COMMENT '群主',
  `notice`       VARCHAR(500) DEFAULT NULL    COMMENT '群公告',
  `member_count` INT NOT NULL DEFAULT 1,
  `max_member`   INT NOT NULL DEFAULT 200,
  `join_mode`    VARCHAR(20) NOT NULL DEFAULT 'INVITE'
                 COMMENT 'INVITE=仅邀请 / APPROVAL=需审核',
  `status`       VARCHAR(20) NOT NULL DEFAULT 'NORMAL',
  ...
  UNIQUE KEY `uk_biz` (`group_type`, `class_id`, `deleted`),  -- 一个班级只能有一个班级群
  KEY `idx_owner` (`owner_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='群聊';
group_type + class_id 上的唯一索引是精髓 它从数据库层面保证「一个班级有且只有一个班级群」。并发下两个人同时触发建群，也只会成功一个，省掉了分布式锁。

chat_group_member —— 群成员（注意和 class_member 的分工）

CREATE TABLE `chat_group_member` (
  `id`                   BIGINT NOT NULL AUTO_INCREMENT,
  `group_id`             BIGINT NOT NULL,
  `user_id`              BIGINT NOT NULL,
  `member_role`          VARCHAR(20) NOT NULL DEFAULT 'MEMBER'
                         COMMENT 'OWNER/ADMIN/MEMBER',
  `group_nickname`       VARCHAR(50) DEFAULT NULL COMMENT '群昵称',
  `mute_until`           DATETIME DEFAULT NULL    COMMENT '禁言截止时间',
  `last_read_message_id` BIGINT NOT NULL DEFAULT 0 COMMENT '已读位点',
  `join_time`            DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  ...
  UNIQUE KEY `uk_group_user` (`group_id`, `user_id`, `deleted`),
  KEY `idx_user` (`user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='群成员';

和 class_member 的区别：班级成员是「教务关系」（谁是这个班的同学），群成员是「聊天关系」（谁在这个群里）。班级群两者会同步，但自建群只有群成员。分开维护，互不污染。

friend_request + friendship —— 好友

CREATE TABLE `friend_request` (
  `id`          BIGINT NOT NULL AUTO_INCREMENT,
  `from_user_id` BIGINT NOT NULL COMMENT '申请人',
  `to_user_id`   BIGINT NOT NULL COMMENT '被申请人',
  `message`     VARCHAR(200) DEFAULT NULL COMMENT '验证消息',
  `status`      VARCHAR(20) NOT NULL DEFAULT 'PENDING'
                COMMENT 'PENDING/ACCEPTED/REJECTED/EXPIRED',
  `handle_time` DATETIME DEFAULT NULL,
  ...
  KEY `idx_to_status` (`to_user_id`, `status`),   -- 查询「待我处理」
  KEY `idx_from` (`from_user_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='好友申请';

CREATE TABLE `friendship` (
  `id`         BIGINT NOT NULL AUTO_INCREMENT,
  `user_a_id`  BIGINT NOT NULL COMMENT '较小的userId',
  `user_b_id`  BIGINT NOT NULL COMMENT '较大的userId',
  `remark_a`   VARCHAR(50) DEFAULT NULL COMMENT 'A给B起的备注',
  `remark_b`   VARCHAR(50) DEFAULT NULL COMMENT 'B给A起的备注',
  `create_time` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  ...
  UNIQUE KEY `uk_pair` (`user_a_id`, `user_b_id`, `deleted`),
  KEY `idx_a` (`user_a_id`), KEY `idx_b` (`user_b_id`)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='好友关系';

备注名也做了双向存储（remark_a / remark_b），因为「我给对方起的备注」是私有数据，不能给对方看到。

05模块一：群聊

群分为「班级群」和「自建群」两类，走同一套底层模型，但成员来源不同。

5.1 两类群的区别

维度班级群自建群
创建方式班级创建时自动生成，一班级一群用户手动创建
成员来源与 class_member 自动同步群主/管理员手动邀请
加群方式加入班级即自动入群，退出班级即自动退群被邀请 / 申请审核
能否解散不能（随班级存亡）群主可以
能否改名跟随班级名群主/管理员可改

5.2 群的创建与成员同步

班级创建时挂一个「确保班级群存在」的钩子

在 ClassServiceImpl.createClass() 里，创建完班级和班级成员后，调用 GroupService.ensureClassGroup(classId)。这个方法内部先查有没有，没有才建 —— 借数据库唯一索引兜底，天然幂等。

班级群创建时同步初始化成员

把 class_member 里的人批量插入 chat_group_member，班级创建者设为群的 OWNER。同时创建对应的 chat_session（biz_key = "G_{groupId}"）和每个成员的 chat_session_user 行。

后续成员变动双向同步

在 ClassServiceImpl.joinClass() / quitClass() 里同步调用群成员的增删；同时给该成员的会话列表插入/移除对应的 chat_session_user。

群变动的实时通知

有人入群后，向群内已在线成员推一条 SYSTEM 类型的消息（「XXX 加入了群聊」），前端在消息流里渲染为居中的灰色提示条。

5.3 群聊消息的扇出过程

群消息与私聊消息最大的区别是「一条消息要发给 N 个人」，这个过程叫扇出。

服务端收到 WS 帧 CHAT_SEND

校验：发送者是否在群里（chat_group_member 有无记录）、是否被禁言、群是否正常。

消息落库

写入 chat_message，拿到自增的 messageId。这是后续一切的基础。

更新会话的最后消息

更新 chat_session.last_message_id / last_message_time，这样所有成员的会话列表排序会自动跟着变。

查成员列表，逐个推送

查出 chat_group_member 里所有 user_id，对每个 id 去 WsSessionRegistry 查有没有在线连接：在线 → 推 CHAT_MESSAGE 帧；不在线 → 什么都不做（靠上线补拉）。

给发送者回执

回推一条 MESSAGE_ACK，带上 clientMsgId 和真实 messageId。前端据此把气泡从「发送中」改为「已发送」。

扇出时的性能注意点 不要在一个循环里逐条 session.sendMessage() 并等待 —— WebSocket 写入是同步 IO，一个人网络卡住会拖慢所有人。正确做法：把这条消息序列化一次，然后遍历推送；对推送异常的连接做剔除而不抛出。如果群很大（几百人），应把扇出丢到独立线程池异步执行，让发送接口立即返回。

5.4 群管理的交互方式

操作权限交互流程
创建群所有用户前端：选择好友 → 填群名 → POST /groups → 返回 groupId → 跳转到该群聊天页 → 被拉的人实时收到 GROUP_INVITE 帧，会话列表出现新群

06模块二：好友系统

参照 QQ 的好友模型：申请 → 通过 → 出现在好友列表 → 可发起私聊。私聊与群聊共用会话和消息表。

6.1 好友申请的状态机

好友申请的每种状态、谁能触发、以及触发后发生什么：

状态触发动作系统副作用
PENDING A 发申请 ① 校验：不能加自己、不能已是好友、不能有反向 pending 申请（防止互相申请）；
② 落库；
③ 若 B 在线，推送 FRIEND_REQUEST 帧，B 的导航栏「新朋友」出现红点。
ACCEPTED B 点同意 ① 写 friendship 一行（小 id 在前）；
② 自动创建私聊会话（biz_key = P_{小id}_{大id}）并为双方各插一行 chat_session_user；
③ 推送 FRIEND_ACCEPTED 给 A，A 的好友列表和会话列表即时出现 B。
REJECTED B 点拒绝 只更新状态。不通知 A（避免尴尬），A 侧看到的一直是「等待验证」。
EXPIRED 7 天未处理 由定时任务扫描改为 EXPIRED（可选，不实现也不影响主流程）。
「同意后自动建会话」是体验的关键 很多简单的实现是「成为好友后，等用户点开聊天框才创建会话」。这样做的后果是：会话列表里不会立刻出现这个人，用户会以为没加上。在同意的一瞬间就把会话建好，双方会话列表立刻出现对方，体验才对。

6.2 添加好友的完整交互链路

A 找到 B 并发送申请

入口有三个：① 班级成员列表点「加好友」；② 同学主页的按钮；③ 搜索框按昵称/真实姓名搜索。点击后弹出对话框填验证消息（默认「我是同班同学 XXX」）→ POST /friends/requests。

B 侧收到实时通知

B 若在线，WS 推送 FRIEND_REQUEST 帧 → Pinia 里 friendStore.pendingCount++ → 左侧导航「新朋友」出现红点 + 轻提示。B 若离线，红点靠下次登录时 GET /friends/requests?status=PENDING 拉出来。

B 处理申请

打开「新朋友」页 → 看到申请卡片（头像、昵称、班级、验证消息）→ 点「同意」→ PUT /friends/requests/{id}/accept。

后端建立双向关系 + 会话

一个 @Transactional 事务里完成：改申请状态 → 插 friendship → 建 session → 插两行 session_user。事务提交后再推送（避免事务未提交就推送，对方点进来查不到数据）。

双方界面即时更新

A 收到 FRIEND_ACCEPTED → 好友列表 +1、会话列表出现 B（带系统提示「你们已成为好友，开始聊天吧」）；B 自己的界面在点同意的响应里直接刷新，无需等推送。

6.3 私聊与群聊的统一

这是整个方案里最省事的设计。私聊和群聊在数据层完全同构，只是 session_type 不同：

私聊会话:  biz_key = "P_2_5"    session_type = PRIVATE
群聊会话:  biz_key = "G_8"      session_type = GROUP

消息表完全相同 → chat_message.session_id 指向其中任意一种

前端渲染差异：
  私聊：对方头像 + 气泡（靠右/靠左）
  群聊：每条消息额外显示发送者头像和昵称（靠左的气泡上方多一行名字）
  → 只是多一个 v-if="session.sessionType === 'GROUP'"

收益：一套消息列表组件 MessageList.vue、一套发送框、一套滚到底部逻辑、一套未读处理，覆盖两种场景。新增私聊功能几乎没有额外前端工作。

6.4 接口清单

GET    /api/friends                     我的好友列表（含在线状态、备注）
DELETE /api/friends/{userId}            删除好友
PUT    /api/friends/{userId}/remark     设置备注名

POST   /api/friends/requests            发起好友申请
GET    /api/friends/requests            收到的申请（?status=PENDING）
GET    /api/friends/requests/sent       我发出的申请
PUT    /api/friends/requests/{id}/accept    同意
PUT    /api/friends/requests/{id}/reject    拒绝

GET    /api/users/search?keyword=xxx    搜索用户（加好友入口）
GET    /api/users/{id}/relation         我与该用户的关系：NONE/PENDING/IS_FRIEND/SELF
/relation 这个接口很实用 同学主页上的按钮要显示「加好友」还是「发消息」还是「等待验证」，全靠这个接口。前端不用自己拼接各种列表去判断，一次请求拿到结论。

    7.2 变量分层架构

    变量不能只有一层。如果组件里直接写 var(--brand)，那么「深色主题下气泡文字要变白」这种需求就没法优雅表达。所以分三层：

    第一层：原始色板（Palette）—— 只定义色值，不含语义
  --c-pink-500: #d94f7c;
  --c-purple-500: #7d6fd0;
  --c-ink-900: #1a1b3a;

第二层：语义变量（Semantic）—— 主题切换的实际操作对象
  --color-bg          页面背景
  --color-surface     卡片/面板背景
  --color-text        主文字
  --color-text-muted  次要文字
  --color-brand       品牌主色
  --color-border      分隔线
  --color-bubble-me   我的气泡底色
  --color-bubble-other 对方气泡底色

第三层：组件变量（Component）—— 少数需要细调的组件
  --chat-input-bg: var(--color-surface);
  --nav-active-bg: var(--color-brand-soft);

    主题切换只动第二层，第一层和第三层都不用碰。组件里永远写 var(--color-*)。

    // stores/theme.js
export const useThemeStore = defineStore('theme', () => {
  const current = ref(localStorage.getItem('theme') || 'sakura')

  function apply(name) {
    current.value = name
    document.documentElement.setAttribute('data-theme', name)
    localStorage.setItem('theme', name)
  }

  function toggle() {
    apply(current.value === 'sakura' ? 'starry' : 'sakura')
  }

  return { current, apply, toggle }
})

    三个必须处理的细节

    • 首屏防闪烁（FOUC）。如果把 data-theme 放在 Vue 挂载后再设置，用户会先看到一帧默认主题再跳变。解决：在 index.html 的 <head> 里放一段内联脚本，在 CSS 加载前就把属性设好。这段脚本必须同步执行，不能 defer。
    • Element Plus 组件要一起变。Element Plus 自带 --el-* 变量，深色主题下要覆盖它，否则弹出框、表格还是白的。在主题块里追加 --el-bg-color、--el-text-color-primary 等映射即可。
    • 装饰动效也要主题化。你现有的 SakuraFall.vue 要把花瓣颜色、数量提成 props，或者读 CSS 变量。星海主题应该是星星闪烁，霓虹主题是光斑游走 —— 否则深色主题下飘着粉色樱花会很怪。

    08消息通道协议

    自定义一套简单 JSON 帧协议。不引 STOMP 的理由是：协议自己定，字段看得见，调试时打开 Network → WS 就能看懂每条帧。

    8.1 连接建立与鉴权

    WebSocket 握手是 HTTP 请求，可以带 token，但浏览器的原生 WebSocket API 不支持自定义请求头，所以不能像普通接口那样发 Authorization 头。三种传法：

    方式说明结论
    URL 查询参数/ws/chat?token=xxx，服务端在 HandshakeInterceptor 里取出来验签采用
    子协议头new WebSocket(url, ['bearer', token])，服务端从 Sec-WebSocket-Protocol 取备选
    连上后再发 AUTH 帧连接先建立，再发一条鉴权帧不推荐
    • 为什么不用第三种：握手时服务端还不知道你是谁，无法在连接建立阶段拒绝非法连接，等于给了攻击者一个白嫖的连接位。放到 URL 参数里，非法 token 直接握手失败，连接根本建立不起来。
    • URL 参数里的 token 会进日志，这点要留意 —— 生产环境应改用一次性 ticket 换连接，毕设场景用 URL 参数完全可接受。
    // 服务端握手拦截器骨架
@Component
public class WsHandshakeInterceptor implements HandshakeInterceptor {
    @Override
    public boolean beforeHandshake(ServerHttpRequest req, ServerHttpResponse resp,
                                   WebSocketHandler h, Map<String, Object> attrs) {
        String token = UriComponentsBuilder.fromUri(req.getURI())
                .build().getQueryParams().getFirst("token");
        Long userId = jwtUtil.parseUserId(token);   // 验签失败返回 null
        if (userId == null) return false;           // 拒绝握手
        attrs.put("userId", userId);                // 传给 Handler
        return true;
    }
}

    8.2 帧协议定义

    统一信封格式，type 决定 data 的结构：

    { "type": "CHAT_SEND", "data": { ... }, "ts": 1759032000000 }

    客户端 → 服务端

    typedata 字段说明
    CHAT_SENDsessionId, msgType, content, extra, clientMsgId发送消息；clientMsgId 用于幂等与回执匹配
    READ_ACKsessionId, lastReadMessageId上报已读，更新 last_read_message_id
    TYPINGsessionId「正在输入」状态，节流发送
    RECALLmessageId撤回消息（2 分钟内）
    PING—心跳，30 秒一次

    服务端 → 客户端

    type说明
    CHAT_MESSAGE新消息推送（私聊或群聊），前端插入消息流 + 更新会话列表 + 未读 +1
    MESSAGE_ACK发送回执，带 clientMsgId 和真实 messageId，前端把气泡标为已发送
    READ_NOTIFY对方已读了你的消息（私聊显示「已读」）
    FRIEND_REQUEST收到新的好友申请，「新朋友」红点 +1
    FRIEND_ACCEPTED你的申请通过了，好友列表与会话列表刷新
    GROUP_INVITE被拉进新群，会话列表新增一项
    GROUP_CHANGED群资料变更 / 被移出 / 群解散，提示并刷新
    ONLINE_STATUS好友上下线，更新在线小绿点
    PONG心跳响应

    8.3 客户端连接管理（ws.js 的职责）

    这一层封装得好不好，直接决定聊天功能稳不稳。必须处理四件事：

    单例连接 + 引用计数

    整个应用只能有一条连接。不要在每个聊天页面里 new WebSocket()，否则来回切页面会建立一堆连接。放在 ws.js 里做单例，登录后建立，退出登录时关闭。

    心跳保活

    每 30 秒发 PING，若 10 秒内没等到 PONG 就判定连接已死，主动重连。没有心跳的话，连接可能已经被中间的代理（比如你提到的 natapp 隧道、Nginx）悄悄断掉，而浏览器还以为连着，消息发出去石沉大海。

    指数退避重连

    断开后按 1s → 2s → 4s → 8s → 最多 30s 的间隔重连，避免服务端刚重启时被大量客户端同时冲击。重连前先刷新 token，因为 JWT 可能已过期，否则会陷入「一直重连一直失败」的死循环。

    重连成功后补拉离线消息

    连接恢复后立刻做两件事：① 拉取会话列表（拿到各会话的最新未读数）；② 对当前打开的会话，按本地最后一条消息 ID 增量拉历史（GET /messages?sessionId=x&afterId=n）。这是保证「断线期间的消息一条都不丢」的关键一步。

    和你 natapp 隧道的一个真实冲突 免费版 natapp 隧道对 WebSocket 的支持不稳定，长连接可能被中途掐断。开发调试时如果发现消息时通时不通，先直连 localhost:5173 验证，排除隧道因素。另外前台演示时，把后端端口也单独映射一条隧道会更稳，或者干脆本地演示不用隧道。

    三个关键顺序：① 前端先本地插入（乐观更新），用户点发送立刻看到气泡，不用等网络；② 服务端先落库再推送；③ 回执与推送是两条独立的帧，前端靠 clientMsgId 匹配。

    09迭代路线

    四轮推进，每轮结束都是一个可以演示的完整状态。不建议一次性全做完，否则出问题很难定位。

    P0打通链路
    • 9 张表的建表脚本 + 实体/Mapper
    • WebSocket 通道（握手鉴权、会话注册表、心跳）
    • 好友申请 → 同意 → 自动建会话
    • 私聊发消息、收消息、历史记录分页
    • 会话列表 + 未读红点

    验收：两个浏览器登录不同账号，能加好友、能实时互发消息、刷新后记录还在。

    P1群聊与主题
    • 班级群自动创建 + 成员同步
    • 自建群、邀请、退群、群管理
    • 群消息扇出 + 发送者展示
    • 5 款主题 + 切换 + 持久化 + 防闪烁
    • Element Plus 变量联动 + 装饰动效主题化

    验收：群里多人聊天正常；切主题后刷新页面主题不丢、无闪白。

    P2体验补齐
    • 在线状态、最后活跃时间

    P3亮点功能
    • 时光胶囊（写往未来的信 + 定时开启）

    10风险与取舍

    提前把坑列清楚，比写完再返工便宜得多。

    风险点说明与应对
    单机会话表
    不支持集群    		 当前方案 Map<userId, Set<Session>> 存在 JVM 内存里，多节点部署会互相看不到。应对：预留 MessagePusher 接口，单机实现是遍历本地会话，未来换成 Redis Pub/Sub 实现即可，上层业务代码不动。
    消息重复 / 丢失 重复：靠 client_msg_id 幂等去重。丢失：靠「先落库再推送」+ 重连后增量补拉。这两条是底线，P0 阶段就要做对。
    聊天内容的 XSS 聊天是最容易出 XSS 的地方——用户可控的任意文本会被渲染。应对：后端落库时用 HtmlUtils 转义，前端渲染用 v-text 或 {{ }}，绝对不能用 v-html（除非是经过白名单过滤的富文本）。
    敏感词与违规内容 你已有 audit_status 审核机制。聊天的应对策略：不入库前审核（影响实时性），而是异步扫描 + 事后处理，或者简单的敏感词命中后替换为 ***，并记一条待审核记录。
    未读数的性能 会话列表如果有 50 个会话，逐个 COUNT 就是 50 次查询。应对：一次 SQL 用 GROUP BY 批量算，或者对不活跃会话懒加载（打开会话时才精确算）。
    主题切换的性能 只改 data-theme 属性触发 CSS 变量重算，代价极低，不需要重新渲染组件树。要避免的是「用 JS 遍历 DOM 改样式」这种写法。
    时间与工作量 P0 是最关键的一轮，占了整体 40% 的复杂度。建议先把 P0 做完并跑通双端互通，再动 P1，否则群聊和主题的改动会让问题定位变得很困难。
    一句话总结这次的架构主线 用「统一会话模型」把私聊和群聊合并成一套；用「HTTP 管状态变更、WS 管实时推送」把两条通道的职责切开；用「CSS 变量三层分层」把主题变成可插拔的配置。三条主线各自独立，互不干扰，所以可以按 P0 → P3 稳步推进。
